# План исследования normative demand

## Цель

Построить сигнал `normative_demand` для сущности `пекарня x SKU x день`,
который:

- более системный, чем фактические продажи;
- легче прогнозируется;
- интерпретируем для бизнеса;
- полезен для планирования выпуска и закупа;
- при этом остается привязанным к реалистичному поведению конкретной пекарни и SKU.

Этот блок **не** ставит целью точно восстановить истинный скрытый спрос.
Задача состоит в том, чтобы сконструировать целевой ряд для планирования,
который будет статистически устойчивым и операционно полезным.

## Ключевые определения

### 1. `observed_sales`

То, что реально было продано.

Свойства:

- отражает реальные транзакции;
- содержит операционный шум;
- может быть искажен цензурированием, stockout, проблемами выкладки,
  ассортиментными разрывами и особенностями работы пекарни.

### 2. `attainable_demand`

Консервативная оценка того, сколько можно было бы продать при лучшем исполнении.

Свойства:

- ближе к потенциальному спросу, чем фактические продажи;
- не считается истиной;
- используется как вспомогательный ориентир, а не как финальный таргет по умолчанию.

### 3. `normative_demand`

Целевой управленческий ряд для обычного дня.

Свойства:

- содержит тренд;
- содержит недельную сезонность;
- допускает изменение амплитуды недельной сезонности во времени;
- намеренно подавляет хаотичный краткосрочный шум;
- на базовом уровне не включает праздники и события;
- должен отражать характерное поведение конкретной пекарни и SKU, а не абстрактную среднюю.

## Бизнес-гипотеза

Фактические продажи слишком хаотичны для устойчивого планирования, потому что
в них смешаны:

- реальный клиентский спрос;
- цензурирование и stockout;
- слабое исполнение внутри пекарни;
- сдвиги ассортимента;
- случайный операционный шум.

Если заменить сырые фактические продажи более структурированным сигналом
`normative_demand`, то:

- предсказуемость должна вырасти;
- планирование должно стать стабильнее;
- выпуск и закуп станет проще операционализировать;
- реакция системы на случайные дневные колебания должна снизиться.

## Главный исследовательский вопрос

Можно ли построить `normative_demand` для `пекарня x SKU x день`, который будет
лучше подходить для планирования, чем `observed_sales`, и при этом не оторвется
слишком сильно от реального поведения пекарни и SKU?

## Что считается успехом

Результат считается успешным, если нормативный ряд:

1. более предсказуем, чем фактические продажи;
2. сохраняет тренд и недельную структуру;
3. менее шумный по дням;
4. остается чувствительным к контексту пекарни и SKU;
5. реально полезен для планирования;
6. не создает систематического давления в сторону перепроизводства.

## Явные не-цели

На этом этапе мы **не** пытаемся:

- точно моделировать истинный скрытый спрос;
- встраивать праздники и спецсобытия в базовый нормативный ряд;
- утверждать, что `normative_demand` равен истинному спросу;
- сразу оптимизировать политику пополнения end-to-end.

Праздники, события и особые дни должны добавляться позже как отдельный слой
корректировок поверх базового нормативного сигнала.

## Слои исследования

### Слой A. Observed Layer

Фактические продажи, сырые или deduplicated.

### Слой B. Attainable Layer

Консервативная execution-aware корректировка фактических продаж.

### Слой C. Normative Layer

Структурированный базовый ряд для обычного дня.

### Слой D. Event Overlay Layer

Отдельные корректировки под праздники, события и особые дни.

Текущий блок сфокусирован на **слое C**, при этом слой B может использоваться
как вспомогательный ориентир.

## Обязательные свойства normative demand

Для каждой пары `пекарня x SKU` нормативный сигнал должен содержать:

- недельную сезонность;
- тренд;
- адаптивную недельную амплитуду;
- ограниченную дневную волатильность;
- устойчивую связь с динамикой самой пекарни;
- интерпретируемую декомпозицию.

Удобная рабочая декомпозиция:

`normative_demand = level * trend * weekday_shape * amplitude_adjustment`

Где:

- `level` — стабильный базовый уровень;
- `trend` — медленное изменение уровня;
- `weekday_shape` — форма недели;
- `amplitude_adjustment` — расширение или сжатие недельного паттерна.

## Контур оценки

Оценка не должна опираться только на forecast-метрики.

### 1. Метрики предсказуемости

Для нормативного таргета и для фактических продаж считаются:

- `MAE`
- `WMAPE`
- `R2`
- устойчивость метрик по rolling windows
- доля рядов с приемлемым качеством

Основное сравнение:

- прогнозирование `observed_sales`
- прогнозирование кандидата `normative_demand`

Если нормативный таргет заметно легче прогнозируется, это положительный сигнал.

### 2. Структурные метрики

Они отвечают на вопрос, действительно ли ряд стал системным:

- сила недельной сезонности;
- устойчивость weekday-профиля;
- гладкость тренда;
- дневная волатильность;
- волатильность недельной амплитуды;
- доля объяснимой и необъяснимой вариации.

### 3. Метрики полезности для планирования

Они отвечают на вопрос, пригоден ли ряд для операционного использования:

- гладкость дневного плана;
- стабильность выпуска по неделям;
- уменьшение резких разворотов плана;
- отсутствие системного завышения относительно разумного базиса;
- совместимость с рабочим масштабом конкретной пекарни.

### 4. Метрики связи с реальностью

Они отвечают на вопрос, не оторвался ли ряд от фактического поведения:

- корреляция с `observed_sales`;
- корреляция с `attainable_demand`;
- согласованность с долями пекарни;
- согласованность с долями SKU внутри пекарни.

## Сегментация до моделирования

Перед построением normative demand каждая пара `пекарня x SKU` должна быть
профилирована.

Нужно построить таблицу `predictability_and_structure_map` со следующими полями:

- средний объем;
- медианный объем;
- доля нулей;
- коэффициент вариации;
- сила недельной сезонности;
- устойчивость weekday-профиля;
- сила тренда;
- нестабильность недельной амплитуды;
- доля цензурированных дней;
- availability / execution сигналы, если доступны;
- корреляция с общими продажами пекарни;
- длина истории;
- доля активных дней.

На основе этой карты ряды должны быть отнесены к предварительным сегментам:

- `stable`
- `noisy`
- `high_censoring`
- `intermittent`
- `bakery_driven`
- `trend_dominated`
- `amplitude_unstable`

Эта сегментация является обязательной предпосылкой для meaningful normative modeling.

## Кандидатные семейства normative-моделей

Не нужно предполагать, что существует одно универсальное правило построения.

### Normative V1. Тренд + статический weekday-профиль

Для каждой пары `пекарня x SKU`:

- оценивается стабильный базовый уровень;
- оценивается тренд;
- оценивается один фиксированный weekday-профиль;
- затем ряд восстанавливается из этих компонент.

Назначение:

- самый простой benchmark;
- интерпретируемая нижняя граница;
- проверка, помогает ли уже простая регуляризация.

### Normative V2. Тренд + адаптивная амплитуда недели

То же, что и V1, но недельная форма может сжиматься и расширяться во времени.

Назначение:

- сохранить недельную структуру;
- допустить реалистичные изменения масштаба недели;
- проверить ключевую гипотезу о нестатичной недельной сезонности.

### Normative V3. Bakery-anchored normative demand

Сначала строится нормативный спрос на уровне пекарни, затем он распределяется
на SKU через устойчивые доли и профили.

Назначение:

- навязать SKU-уровню логику работы пекарни;
- уменьшить SKU-хаос за счет опоры на bakery-level поведение.

### Normative V4. Bakery anchor + SKU residual

Bakery-level normative demand используется как backbone, а SKU-модель учит
только устойчивый остаточный паттерн.

Назначение:

- сделать поведение пекарни главным якорем;
- сохранить индивидуальность SKU там, где она достаточно устойчива.

## Правило выбора лучшей normative-модели

Побеждает **не** самая гладкая модель.

Победитель должен:

- улучшать предсказуемость;
- сохранять реалистичную bakery/SKU структуру;
- уменьшать операционный шум;
- не создавать систематической инфляции объема.

Выбор должен основываться на комбинированной оценке по четырем блокам:

- предсказуемость;
- структура;
- полезность для планирования;
- близость к реальному поведению.

## Первые три эксперимента

### Experiment N1. Карта предсказуемости и структуры

Цель:

- количественно понять, из чего состоит хаос;
- определить, какие ряды вообще пригодны для normative-моделирования.

Входы:

- deduplicated bakery/SKU daily data;
- при наличии — артефакты attainable demand.

Выходы:

- `predictability_and_structure_map.csv`
- `segment_summary.csv`
- `segment_examples.csv`

Главные вопросы:

- какая доля вариации структурна, а какая похожа на шум;
- какие пары bakery x SKU bakery-driven;
- какие пары слишком intermittent или слишком зацензурированы.

### Experiment N2. Базовый normative V1

Цель:

- построить первый нормативный ряд через тренд + статический weekday-паттерн.

Выходы:

- `normative_v1_daily.csv`
- `normative_v1_summary.json`
- сравнение метрик против фактического таргета.

Правило интерпретации:

- если V1 не дает заметного выигрыша по предсказуемости, значит дальше
  потребуется более сильный bakery-anchor или более глубокая сегментация.

### Experiment N3. Normative V2 с адаптивной амплитудой

Цель:

- проверить, является ли адаптивная амплитуда той самой недостающей структурной частью.

Выходы:

- `normative_v2_daily.csv`
- `normative_v2_summary.json`
- сравнение с V1 на одном и том же наборе рядов.

Правило интерпретации:

- если V2 улучшает и структурную реалистичность, и предсказуемость, то
  адаптивная амплитуда становится частью базового design contract.

## Рекомендуемый порядок выполнения

1. Построить profiling map.
2. Сегментировать пары `пекарня x SKU`.
3. Построить V1 normative baseline.
4. Построить V2 normative baseline с адаптивной амплитудой.
5. Сравнить V1 и V2 по forecastability и planning-метрикам.
6. Только после этого решать, становится ли bakery-anchored V3 основным направлением.

## Практический контракт по артефактам

Каждый normative-эксперимент должен сохранять:

- `metrics.json`
- `summary_by_segment.csv`
- `summary_by_bakery.csv`
- `summary_by_sku.csv`
- `examples_good.csv`
- `examples_bad.csv`
- `predictions_or_reconstruction.csv`

Если артефакты становятся слишком тяжелыми, полные данные хранятся в
`data/processed`, а компактные summary — в директории эксперимента.

## Базовые допущения, которые сохраняем

- Базовый normative demand описывает только обычные дни.
- Праздники и события добавляются позже как отдельный корректирующий слой.
- Поведение самой пекарни, вероятно, важнее многих внешних регрессоров.
- Не каждый SKU должен моделироваться с одинаковой степенью свободы.
- Полезный planning target может быть важнее шумного "truth-like" таргета.

## Ближайший следующий шаг

Реализовать **Experiment N1**:

- построить profiling table для всех `пекарня x SKU`;
- посчитать признаки предсказуемости, структуры и bakery-зависимости;
- кластеризовать или rule-сегментировать ряды;
- использовать эту карту как основу для всех следующих normative-demand экспериментов.
