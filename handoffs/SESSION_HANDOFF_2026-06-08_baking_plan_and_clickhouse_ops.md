# Session Handoff - 2026-06-08 - Baking Plan and ClickHouse Ops

## Current Decision: VM vs ClickHouse

We revisited production infrastructure because the current VM is small and
resource constrained.

Known production VM constraint:

- around 1.9 GiB RAM before swap;
- recent SKU correction previously caused an OOM kill;
- swap was added as a workaround;
- production path was narrowed to one scenario (`uplifted_norm`) to reduce
  memory pressure.

Earlier "large VM" sizing such as roughly 8 vCPU / 16 GB RAM applied to a full
local production factory where the VM would rebuild raw snapshots, profiles,
models, forecasts, allocations, and serving outputs in pandas/CSV.

The current preferred direction is different:

- keep the small VM for scheduling, LightGBM inference, API/backend, activation,
  and Excel generation;
- move heavy aggregations and profile/allocation recalculations into
  ClickHouse.

## Operations To Move To ClickHouse Later

Good candidates:

- monthly bakery revenue and revenue bucket for baking plan template selection;
- bakery daily/hourly aggregates;
- `bakery_hour_profile`;
- raw `sku_hour_share_profile`;
- SKU profile smoothing and renormalization by `bakery_id + dow + hour`;
- SKU uplift multipliers;
- recent assortment/freshness stats;
- bakery-day to bakery-hour allocation;
- bakery-hour to SKU-hour allocation;
- recent correction such as `blend_recent_50`;
- direct insert into `sku_forecast_hour_embedded` and
  `sku_forecast_day_embedded`.

Keep on VM/off-box:

- LightGBM inference;
- LightGBM retraining;
- app/backend;
- Excel export;
- scheduler that sends SQL commands to ClickHouse;
- run comparison/activation orchestration.

Important nuance:

- moving only the SKU profile table to ClickHouse is not enough;
- the largest remaining VM pressure is generated by allocation and recent
  correction, especially when the full SKU-hour forecast is read back into
  pandas;
- the highest-leverage future change is direct ClickHouse SQL allocation and
  correction without large intermediate CSV files on the VM.

For now we explicitly keep the current production setup as-is and continue with
the baking plan feature.

## Baking Plan Feature Direction

User provided workbook:

`C:\Users\dns\Downloads\План выпекания с 4 утра по выручкам.xlsx`

Workbook structure:

- 4 sheets by monthly revenue bucket:
  - `до 1,5 млн`
  - `до 2,5 млн`
  - `от 2,5 млн`
  - `от 3млн`
- columns `A:B`: station/role and SKU name;
- columns `C:L`: baking windows from `4:00-7:00` through `15:00-16:00`;
- columns `M:P`: manual production/task notes;
- no formulas; values are static plan quantities and task text.

Desired business logic:

1. For selected bakery and forecast date, get SKU-hour forecast from
   `sku_forecast_hour_embedded`.
2. Determine revenue bucket from a future monthly ClickHouse table.
3. Select the matching baking-plan template sheet.
4. For each SKU, read the baking windows available in the template.
5. Convert baking windows into demand coverage intervals:
   - each baking window covers forecast sales until the next baking window;
   - example: if SKU bakes at `4:00-7:00` and next at `11:00-12:00`, the first
     window covers sales from early opening hours up through hour `11`; hour
     `12` belongs to the next baking window.
6. Cell value equals the sum of forecast SKU sales in the covered hours,
   rounded to production-friendly quantities.

Open implementation details:

- exact hour boundary convention must be fixed and tested;
- SKU names in the template need mapping to ClickHouse `product_id`;
- per-SKU batch/rounding rules are needed for production-quality output;
- month revenue should be precomputed monthly in ClickHouse, not calculated on
  every Excel request.

Planned MVP:

- add app action to download an Excel baking plan for selected bakery/date;
- use active forecast run;
- use the selected revenue bucket/template;
- generate a workbook matching the current layout;
- preserve task-note columns where possible;
- start with simple rounding, then add SKU-specific batch rules.
