# Pilot Management Reporting Contract

## 1. Назначение

Этот документ задаёт целевую архитектуру управленческой отчётности пилота
прогнозирования спроса. Контракт нужен, чтобы приложение, Excel-выгрузки и
аналитические отчёты использовали один набор данных, формул и организационных
связей.

Отчётность должна раздельно отвечать на четыре вопроса:

1. насколько прогноз соответствует оценочному спросу;
2. насколько пекарня следует плану;
3. как меняются продажи, упущенный спрос и другие бизнес-показатели;
4. где требуется управленческое вмешательство.

Пороговые значения, окончательный состав товарного контура и правила оценки
экономического эффекта утверждаются отдельно. До утверждения они должны
храниться как версионируемые параметры, а не быть неявно зашиты в интерфейс.

## 2. Границы контуров

### 2.1. Операционное планирование

Ежедневный publisher и план выпекания являются forward-looking контуром. Они
отвечают на вопрос, сколько продукции подготовить к продаже, и могут учитывать:

- прогноз спроса;
- остаток со вчерашнего дня;
- чистую потребность;
- кратность;
- план выпуска;
- итоговое количество на продажу;
- производственные ограничения и окна выпуска.

Publisher не является источником управленческих KPI пилота и не должен
самостоятельно рассчитывать качество прогноза или исполнения.

### 2.2. Оценка пилота

Evaluation-контур является backward-looking. Он сопоставляет фактически
выданный прогноз и план с фактом, известным после завершения дня. Историческая
оценка должна использовать снимок, действительно доступный пользователю до
оцениваемого дня, а не текущий активный прогноз.

Evaluation-контур является единственным источником формул для приложения,
управленческой сводки и Excel-экспорта результатов.

## 3. Версионируемый состав пилота

Состав пилота задаётся отдельной сущностью `pilot_scope`, а не списком в коде
отчёта.

Минимальные поля:

| Поле | Назначение |
|---|---|
| `scope_version` | Стабильный идентификатор версии состава |
| `scope_name` | Читаемое название |
| `valid_from` / `valid_to` | Период действия версии |
| `bakery_id` | Пекарня в контуре |
| `category_id` или нормализованная категория | Категориальный фильтр, если применяется |
| `product_id` | Явное включение или исключение SKU, если применяется |
| `inclusion_mode` | Способ задания: bakery/category/SKU |
| `is_included` | Включение или исключение |
| `reason` | Основание изменения состава |
| `source_ref` | Ссылка на решение или источник, если имеется |
| `loaded_at` | Время загрузки версии |

Известные рабочие контуры необходимо различать:

- `base_pilot_10` — базовый пилот из 10 пекарен; Кулагина 4 в него не входит;
- `expanded_pilot_38` — расширенный контур из 38 пекарен, используемый в
  отдельных текущих модельных и профильных работах.

Нельзя автоматически считать, что `expanded_pilot_38` заменил
`base_pilot_10` в управленческой оценке. Для каждого отчёта обязательно
указывать `scope_version`. Точный список 38 пекарен и дата начала их
управленческой оценки должны быть подтверждены источником до публикации KPI.

Покупные товары, напитки, пакеты и новые производственные категории не должны
попадать в основной показатель только на основании наличия продаж. Включение
хлеба, кондитерки, фастфуда и шведской линии оформляется новой версией scope или
отдельным контуром.

## 4. Канонический факт `pilot_performance_sku_day`

### 4.1. Grain

Одна строка соответствует:

`scope_version × metric_version × forecast_date × bakery_id × product_id`

Если за день существовало несколько прогнозов, в строку попадает только снимок,
выбранный утверждённым правилом публикации. Его происхождение сохраняется в
полях lineage.

### 4.2. Идентификаторы и lineage

| Поле | Назначение |
|---|---|
| `forecast_date` | Оцениваемый операционный день |
| `bakery_id`, `bakery_name` | Пекарня |
| `product_id`, `product_name` | SKU |
| `category_id`, `category_name` | Нормализованная категория |
| `scope_version` | Версия состава пилота |
| `metric_version` | Версия формул и порогов |
| `ownership_version` | Версия организационной иерархии |
| `source_run_id` | Run выданного прогноза |
| `forecast_origin_date` | Дата происхождения прогноза |
| `lead_days` | Горизонт снимка |
| `forecast_generated_at` | Время генерации снимка |
| `plan_version` | Версия фактически опубликованного плана, если доступна |
| `calculated_at` | Время расчёта строки |

### 4.3. Исходные величины

| Поле | Назначение |
|---|---|
| `forecast_qty` | Фактически выданный прогноз спроса |
| `previous_day_stock_qty` | Остаток, использованный при формировании плана |
| `net_need_qty` | Чистая потребность плана |
| `production_plan_qty` | Опубликованный план выпуска |
| `total_for_sale_plan_qty` | План выпуска плюс учтённый остаток |
| `production_qty` | Фактический выпуск за день |
| `sales_qty` | Фактические продажи |
| `closing_stock_qty` | Зафиксированный остаток |
| `last_sale_at` | Время последней продажи, если доступно |
| `revenue` | Фактическая выручка, если достоверно связана со строкой |

Поля плана должны хранить опубликованные значения. Их нельзя задним числом
восстанавливать из текущей версии алгоритма, если версия фактически отправленного
плана неизвестна.

### 4.4. Производные величины

| Поле | Назначение |
|---|---|
| `lost_demand_qty` | Оценка упущенного спроса по версии методики |
| `demand_qty` | `sales_qty + lost_demand_qty` |
| `forecast_error_qty` | Знаковое отклонение прогноза от спроса |
| `forecast_abs_error_qty` | Абсолютная ошибка прогноза |
| `forecast_error_ratio` | Относительная ошибка при допустимом знаменателе |
| `execution_error_qty` | Знаковое отклонение исполнения от выбранной базы плана |
| `execution_abs_error_qty` | Абсолютное отклонение исполнения |
| `execution_error_ratio` | Относительное отклонение исполнения |
| `forecast_status` | `underforecast` / `normal` / `overforecast` / `not_scored` |
| `execution_status` | `underproduction` / `normal` / `overproduction` / `not_scored` |
| `is_full_realization` | Признак полной реализации по версии методики |
| `is_actionable_exception` | Попадание в очередь управленческих исключений |
| `exception_priority` | Приоритет после утверждения правил ранжирования |

Знак обеих ошибок и база сравнения исполнения должны быть явно определены в
`metric_version`. До утверждения нельзя считать, что фактический выпуск всегда
сравнивается непосредственно с сырым прогнозом: опубликованный план может быть
изменён остатком, кратностью или производственными ограничениями.

## 5. Версия методики

`metric_version` должна ссылаться на конфигурацию, содержащую как минимум:

- формулу и параметры упущенного спроса;
- условие полной реализации;
- время окончания периода продаж;
- правила работы с последней продажей и средней скоростью продаж;
- знаменатели относительных показателей и обработку нулей;
- пороги статусов прогноза;
- пороги и базу статусов исполнения;
- правила для двухдневной продукции;
- правила обработки возвратов, отрицательных остатков и корректировок учёта;
- правила исключения неполного дня;
- правила ранжирования существенности;
- версию товарного классификатора.

Изменение любого из этих правил создаёт новую версию. Исторические отчёты
пересчитываются только осознанно и должны показывать использованную версию.

## 6. Организационная иерархия

Связи ответственности задаются temporal-справочником `bakery_ownership`:

| Поле | Назначение |
|---|---|
| `ownership_version` | Версия снимка оргструктуры |
| `company_id`, `company_name` | Компания |
| `director_id`, `director_name` | Операционный или региональный директор |
| `partner_id`, `partner_name` | Партнёр |
| `bakery_id`, `bakery_name` | Пекарня |
| `valid_from` / `valid_to` | Период ответственности |
| `source` | Источник связи |
| `loaded_at` | Время загрузки |

Таблица доступа Bitrix не заменяет оргструктуру: доступ пользователя и
управленческая ответственность являются разными понятиями. Неизвестная связь
не заполняется предположением; строка маркируется как `ownership_missing`.

## 7. Агрегация

Все уровни используют строки `pilot_performance_sku_day` после применения
одинаковых scope, metric и ownership versions.

Поддерживаемые периоды:

- день;
- полная неделя;
- месяц;
- период пилота;
- сравнимый допилотный период, когда методика сравнения утверждена.

Поддерживаемые уровни:

`company → director → partner → bakery → SKU`

Минимальные агрегаты:

- сумма прогноза, плана, выпуска, продаж, упущенного и итогового спроса;
- сумма знаковой и абсолютной ошибки;
- WAPE или иной взвешенный показатель из сумм, а не среднее процентов строк;
- агрегированный bias;
- количество и доля строк каждого статуса;
- количество проблемных bakery-days и SKU-days;
- выручка и её динамика при наличии сопоставимых данных;
- показатели полноты и качества данных.

Статус группы не следует получать простым большинством статусов SKU. Правило
статуса группы и порог `normal` должны быть утверждены в `metric_version`.

Составные показатели встречи считаются как пересечения независимых статусов:

- норма исполнения при норме прогноза;
- норма исполнения при недопрогнозе;
- норма исполнения при перепрогнозе;
- норма прогноза при перевыпуске;
- норма прогноза при недовыпуске.

В интерфейсе для них следует показывать и количество, и долю от явно указанного
знаменателя.

## 8. Executive drill-down

Главный экран открывается на уровне компании и показывает:

- scope, период и версии расчёта;
- качество прогноза отдельно от качества исполнения;
- продажи, упущенный спрос и выручку;
- динамику относительно выбранного сопоставимого периода;
- число директоров, партнёров и пекарен, требующих внимания;
- рейтинг существенных исключений;
- предупреждения о качестве данных.

Переходы должны сохранять период и версии:

1. компания → список директоров;
2. директор → партнёры и пекарни зоны ответственности;
3. партнёр → принадлежащие ему пекарни;
4. пекарня → динамика и проблемные SKU;
5. SKU → дневной и при необходимости почасовой разбор, комментарии и lineage.

По умолчанию показываются существенные и повторяющиеся отклонения. Полный реестр
остаётся доступен через фильтр или экспорт. Комментарии РД являются объясняющим
слоем и не изменяют рассчитанные факты или статусы.

## 9. Data-quality flags

Строка может иметь несколько флагов. Минимальный набор:

- `forecast_snapshot_missing`;
- `published_plan_missing`;
- `sales_missing`;
- `production_missing`;
- `closing_stock_missing`;
- `negative_stock_observed`;
- `production_sales_inconsistent`;
- `partial_day`;
- `bakery_closed_or_inactive`;
- `scope_mapping_missing`;
- `ownership_missing`;
- `category_mapping_missing`;
- `two_day_rule_unresolved`;
- `lost_demand_not_estimable`;
- `duplicate_source_rows`;
- `source_loaded_late`;
- `metric_not_comparable`.

Флаги не обязаны означать ошибку пекарни или модели. Они определяют пригодность
строки к конкретной метрике. Для каждой метрики контракт должен задавать:

- какие флаги исключают строку;
- какие оставляют строку, но показывают предупреждение;
- количество исключённых строк и их долю.

Исходные отрицательные или спорные значения не исправляются молча. Очистка для
расчёта хранится отдельно от исходного факта и сопровождается правилом версии.

## 10. Serving и интерфейсы

Рекомендуемый минимальный набор:

1. каноническая таблица или материализованный слой
   `pilot_performance_sku_day`;
2. справочники `pilot_scope` и `bakery_ownership`;
3. единый query/service слой с параметрами `scope_version`, `metric_version`,
   период, уровень и идентификатор родителя;
4. при необходимости производительности — периодический агрегат, построенный
   только из канонического слоя;
5. API для summary, hierarchy children, exceptions, SKU detail и export.

Embedded-приложение и Excel должны обращаться к одному service layer. Excel не
должен содержать альтернативную реализацию упущенного спроса, статусов или
агрегаций.

## 11. Этапы внедрения

### Этап 1. Подтверждение бизнес-контракта

- утвердить назначение `base_pilot_10` и `expanded_pilot_38`;
- подтвердить товарный контур;
- утвердить формулы, знаки, пороги и знаменатели;
- определить источник оргструктуры;
- определить правило выбора опубликованного прогноза и плана.

### Этап 2. Канонический SKU-day слой

- собрать causal forecast lineage и факты;
- реализовать версионированные метрики;
- добавить DQ flags;
- сверить известные кейсы вручную;
- сопоставить итоги с существующим недельным Excel.

### Этап 3. Иерархия и агрегаты

- загрузить temporal ownership;
- реализовать day/week/month/pilot агрегации;
- проверить аддитивность сумм и корректность взвешенных метрик;
- добавить очередь существенных исключений.

### Этап 4. Управленческий интерфейс

- добавить executive summary;
- реализовать drill-down до SKU;
- показывать качество данных и lineage;
- перенести Excel-экспорт на общий service layer.

### Этап 5. Приёмка

- бизнес-проверка на нескольких директорах, партнёрах и пекарнях;
- параллельная сверка с текущими отчётами;
- фиксация допустимых расхождений;
- публикация версии контракта и даты начала официального использования.

### Этап 6. Расширение

- подключать новые пекарни новой версией scope;
- новые категории оценивать отдельным контуром до подтверждения сопоставимости;
- не смешивать результаты разных scope и metric versions без явного разреза.

## 12. Критерии готовности первой версии

Первая версия считается готовой, когда:

- любой показатель на экране воспроизводится из канонического SKU-day слоя;
- прогноз и исполнение оцениваются независимо;
- отчёт однозначно указывает scope, период и версии методики;
- агрегат раскрывается от компании до исходных SKU-дней;
- Excel и приложение дают одинаковые итоги;
- исключённые из расчёта строки видимы и объяснимы;
- изменение состава пилота или оргструктуры не требует изменения формул;
- ежедневный publisher не содержит дублирующей логики оценки пилота.
