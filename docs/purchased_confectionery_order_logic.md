# Логика заказа покупной кондитерки

Статус: черновик для пилота после встречи 22.09.2026.

## Контекст

Покупную кондитерку нельзя считать тем же способом, что выпечку и покупной хлеб.

- Выпечка и покупной хлеб в текущем контуре ближе к однодневной логике: прогноз
  на день превращается в выпуск/заказ на день.
- Кондитерка живёт несколько дней, поставляется упаковками и может продаваться
  из запаса несколько суток.
- Остатки в учёте пока нельзя считать надёжным источником истины: приёмка,
  списания и корректировки могут проводиться с задержкой, поэтому автоматическое
  вычитание остатков может занизить заказ.

Поэтому для кондитерки нужен отдельный слой: не «сколько выпечь», а «сколько
заказать до следующего завоза».

## Цель пилота

Проверить, можем ли мы давать полезную рекомендацию заказа по покупной
кондитерке, используя:

1. темп продаж SKU в конкретной пекарне;
2. время, когда SKU, вероятно, отсутствовал до следующего завоза;
3. кратность упаковки;
4. срок хранения как ограничение против чрезмерного заказа;
5. остатки только как вспомогательный, а не обязательный источник.

## Область применения

Первая версия применяется только к покупным категориям:

- `Пирожные`;
- `Маффин Печенье Донатс`;
- `Торты Рулеты`.

`Хлеб` остаётся в отдельной однодневной логике: кратность 1, переходящий остаток
не используется.

## Основные сущности

### Темп продаж

Темп продаж — это оценка, сколько единиц SKU продаётся за час, когда товар
реально есть на витрине.

Базовая формула:

```text
sales_rate_per_hour = продажи_в_период_наличия / часы_наличия
```

Для пилота лучше считать робастно:

- брать последние 4–5 недель;
- сравнивать одинаковые дни недели отдельно, если истории достаточно;
- при малой истории переходить к рабочий/выходной;
- отбрасывать явно аномальные дни;
- использовать медиану или усечённое среднее по дневным темпам.

### Вероятное отсутствие

Так как остатки ненадёжны, факт отсутствия в первой версии определяем не из
остатка, а из поведения продаж.

Кандидат на отсутствие:

```text
последняя продажа SKU была заметно раньше конца периода продаж,
после неё продаж не было,
при этом раньше в этот день SKU продавался нормальным темпом
```

Для расчёта:

```text
absence_hours = часы_от_последней_продажи_до_следующего_завоза_или_конца_периода
```

Важно: это не доказанный факт отсутствия, а сигнал. Поэтому в отчёте нужно
показывать статус, например:

- `подтверждённое отсутствие` — если есть надёжный нулевой остаток или ручная
  отметка;
- `вероятное отсутствие по продажам` — если есть только паттерн продаж;
- `нет сигнала отсутствия` — если продаж было мало или паттерн неубедительный;
- `недостаточно данных`.

### Оценка упущенного спроса

```text
lost_units = sales_rate_per_hour * absence_hours
```

Чтобы не разгонять заказ из-за шумов, на первом этапе нужно ограничить значение:

```text
lost_units_capped = min(lost_units, cap)
```

Варианты cap:

- не больше `x%` от обычного спроса на период;
- не больше `N` упаковок;
- не больше исторического p75/p90 продаж этого SKU за сопоставимый период.

Рекомендуемый старт для пилота:

```text
cap = min(обычный_спрос_на_период * 0.5, 2 упаковки)
```

То есть сигнал отсутствия может усилить заказ, но не должен сразу удваивать его
без проверки.

## Расчёт рекомендации заказа

Для следующего периода до завоза считаем:

```text
base_demand = ожидаемый спрос на период до следующего завоза
stockout_uplift = lost_units_capped из последних сопоставимых периодов
raw_need = base_demand + stockout_uplift
```

Дальше применяем срок хранения и кратность.

### Ограничение сроком хранения

Если срок хранения известен:

```text
max_reasonable_units = sales_rate_per_hour * часы_продаж_за_срок_хранения
raw_need = min(raw_need, max_reasonable_units)
```

Если срок хранения неизвестен, строку не выбрасываем, но помечаем:

```text
нет данных по сроку хранения
```

В этом случае рекомендацию можно считать, но в статусе должно быть видно, что
это менее надёжный расчёт.

### Округление до кратности

Если кратность известна:

```text
order_units = ceil(raw_need / kratnost) * kratnost
order_packs = order_units / kratnost
```

Если кратность неизвестна:

- строку оставляем;
- пишем `нет данных по кратности`;
- для пилота можно показывать `raw_need`, но не выдавать автоматический заказ в
  упаковках.

## Как обращаться с остатками

Первая версия не должна автоматически вычитать системный остаток из заказа.

Причина: на встрече зафиксировали, что остатки могут быть неверными из-за
задержек приёмки, списаний и ошибок проведения документов.

Разрешённые варианты использования остатков:

1. **Не использовать остаток** — безопасный режим пилота.
2. **Показывать остаток справочно** — если значение есть, но не влияет на заказ.
3. **Вычитать только подтверждённый остаток** — если источник/пекарня прошли
   проверку качества учёта.

Для пилота стартовый режим:

```text
остаток показываем справочно, но raw_need не уменьшаем
```

Исключение можно делать только для ручного подтверждения: если пекарня/РД
подтвердили фактический остаток, тогда:

```text
raw_need = max(raw_need - confirmed_stock, 0)
```

## Что показывать бизнесу

Для каждой строки SKU/пекарня:

| Поле | Смысл |
| --- | --- |
| Пекарня | Точка заказа |
| Категория | Покупная категория |
| SKU | Номенклатура |
| Темп продаж | Ед./час при наличии |
| Последняя продажа | Время последней продажи в опорном периоде |
| Вероятное отсутствие, ч | Сколько часов товар мог отсутствовать |
| Оценка упущенного, шт | `sales_rate_per_hour * absence_hours` |
| Базовый спрос до завоза | Ожидаемый спрос без uplift |
| Рекомендация, шт | После uplift и ограничений |
| Кратность | Размер упаковки или `нет данных по кратности` |
| Рекомендация, упак. | Округление до упаковок |
| Срок хранения | Можно показывать отдельно в диагностике; в партнёрском файле допустимо оставлять текущую договорённость через статус |
| Статус | `ok`, `нет кратности`, `нет срока`, `мало данных`, `вероятное отсутствие` |

## Пилотная проверка

Минимальный тест на одну неделю:

1. Выбрать 5–10 SKU кондитерки с частыми продажами.
2. Выбрать ограниченный набор пекарен, где РД/администраторы готовы сверять
   наличие.
3. Каждый день фиксировать:
   - рекомендацию заказа;
   - фактический заказ;
   - продажи;
   - время первой и последней продажи;
   - были ли реальные остатки/отсутствие на витрине;
   - списания, если их можно получить.
4. Сравнить:
   - где рекомендация поймала реальное отсутствие;
   - где создала риск перезаказа;
   - где не сработала из-за отсутствия кратности/срока хранения;
   - насколько часто системный остаток противоречил факту.

## MVP-алгоритм для расчёта

На вход:

- `bakery_id`;
- `product_id`;
- продажи с timestamp;
- календарь/часы работы пекарни;
- дата/время следующего завоза или период заказа;
- кратность упаковки;
- срок хранения, если известен.

Шаги:

1. Собрать историю последних 4–5 недель по SKU/пекарне.
2. Оценить `sales_rate_per_hour` по периодам, где были продажи.
3. Найти последние продажи в опорных днях.
4. Оценить `absence_hours` до следующего завоза/конца периода.
5. Посчитать `lost_units`.
6. Ограничить `lost_units` через cap.
7. Посчитать `base_demand` на следующий период.
8. Добавить `stockout_uplift`.
9. Ограничить сроком хранения.
10. Округлить до кратности.
11. Проставить статус качества расчёта.

## Что не делаем в первой версии

- Не считаем остатки источником истины.
- Не делаем автоматический заказ без пилотной проверки.
- Не смешиваем кондитерку с выпечкой в одной метрике качества.
- Не считаем отсутствие доказанным только потому, что продажи закончились рано.
- Не выбрасываем SKU без кратности/срока, а явно помечаем проблему данных.

## Следующий практический шаг

Собрать диагностическую таблицу за последнюю завершённую неделю по покупной
кондитерке:

- пекарня;
- SKU;
- продажи;
- первая/последняя продажа;
- оценочный темп продаж;
- вероятные часы отсутствия;
- оценка упущенного;
- кратность;
- срок хранения;
- расчётная рекомендация в штуках и упаковках;
- статус качества расчёта.

После просмотра этой таблицы можно выбрать пилотные SKU/пекарни и уже затем
решать, внедрять ли расчёт в партнёрский Excel.
